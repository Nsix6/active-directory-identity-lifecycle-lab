# AD Identity Lifecycle Checklist

This checklist defines planned controls for John's identity lifecycle in the fictional NDIA test environment.

**Day 4 design refinement:** The [domain and OU design](../../day-04-directory-basics/architecture/ad-domain-design.md) places `Technology` and `Security` under `NDIA/Users` in `adlab.test`, while `DisabledUsers` remains under `NDIA`. That design supplies full directory paths and adds team-group membership changes alongside the resource-access changes below; these are planned refinements, not deployed changes.

## Joiner — John joins Engineering

**Scenario:** John joins Technology Services as a Software Engineer on the Engineering team. He needs a standard AD user account and approved access to the Engineering Project Share.

**Status:** Planned. Account creation, access changes, and verification have not been executed in AD.

The account name `john.test` and security group `Engineering_Project_RW` are proposed lab names; this document does not establish that they already exist.

| Required field | Joiner control                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner          | HR confirms John's employment and start date. The Technology Services Manager approves Engineering Project Share access. An IT administrator creates the account, assigns the approved access, and verifies the result.                                                                                                                                                                                                                                                                   |
| Trigger        | An approved onboarding request contains John's identity details, role, department, manager, and confirmed start date. Provisioning follows that request, with account activation scheduled for the approved start date.                                                                                                                                                                                                                                                                   |
| Access change  | Create the standard AD user account `john.test` in the existing `Technology` OU. Set the department to Technology Services, the job title to Software Engineer, and the manager to the approved manager. Add the account to `Engineering_Project_RW`, configured to allow reading, creating, and editing Engineering Project Share files. Do not grant share-permission management rights or privileged administrative group memberships. OU placement alone does not grant share access. |
| Verification   | Check that the account has the approved attributes, OU placement, activation state, and group memberships. After activation, sign in with the test account and confirm that John can read, create, and edit a disposable test file in the Engineering Project Share. Confirm that John cannot change share permissions or access a separately restricted departmental resource. Compare all assigned access with the approved request and record expected and actual results.             |
| Rollback       | If onboarding fails or the wrong account or access is provisioned, disable the newly created account and remove the group memberships added by this onboarding event. Retain the disabled account and the request/change record for investigation. Correct the request or configuration and obtain any necessary approval before retrying and re-enabling the account.                                                                                                                    |

### Planned execution checklist

- [ ] Confirm the HR onboarding request and manager's access approval.
- [ ] Create the standard test account in the `Technology` OU with the approved attributes.
- [ ] Assign the approved Engineering security group membership and activate the account on the approved date.
- [ ] Verify both permitted actions and denied actions using the test account.
- [ ] Record sanitized evidence, expected results, actual results, and any differences.
- [ ] If provisioning fails, perform and record the rollback before retrying.

## Mover — John transfers to Security Operations

**Scenario:** John moves from Software Engineer in Technology Services to Security Operations Analyst in Security Operations. His Engineering Project Share access changes to read-only for an approved monitoring need, and he receives read access to a test Security Monitoring Logs share.

**Status:** Planned. Account updates, access changes, and verification have not been executed in AD.

The role, Security Monitoring Logs share, and groups `Engineering_Project_Read` and `Security_Monitoring_Read` are proposed lab definitions. Retaining Engineering read access requires the Technology Services Manager's approval; it is not automatically granted to every Security Operations user.

| Required field | Mover control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner          | HR confirms the transfer and effective date. The Technology Services Manager approves any retained Engineering access, and the Security Operations Manager approves the new monitoring access. An IT administrator implements and verifies the changes.                                                                                                                                                                                                                                                                                                                                                                                                           |
| Trigger        | An approved transfer request identifies John's new role, department, manager, effective date, access to remove, and access to grant or retain.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Access change  | Record the existing account attributes, OU, and resource-access memberships before changing them. Keep the same `john.test` account; update the department to Security Operations, title to Security Operations Analyst, and manager to the approved new manager. Move the account from the `Technology` OU to the existing `Security` OU. Remove `Engineering_Project_RW` and any other access no longer justified by the new role. Add the approved `Engineering_Project_Read` and `Security_Monitoring_Read` memberships. Configure these groups for read-only access to their respective test shares, without administrative or permission-management rights. |
| Verification   | Check the updated attributes, OU placement, and group memberships against the transfer request. Review the policies applying in the destination OU. Using a fresh test sign-in, verify that John can read Engineering project files but cannot create or edit them, and can read the Security Monitoring Logs share. Check for direct permissions or other group memberships that could still grant Engineering write access. Record expected and actual results, including any old access that remains unexpectedly available.                                                                                                                                   |
| Rollback       | If the transfer changes fail or grant incorrect access, remove the newly assigned access and record the failure. Restore the previous attributes, OU placement, and resource-access memberships from the recorded state only if the transfer is postponed or cancelled and the responsible managers approve restoration. If the transfer remains effective, correct the new role's access rather than restoring obsolete Engineering write access. Repeat verification before closing the request.                                                                                                                                                                |

### Planned execution checklist

- [ ] Confirm the transfer request, effective date, and both managers' access approvals.
- [ ] Record the original attributes, OU, and resource-access group memberships.
- [ ] Update the existing account and remove obsolete Engineering access.
- [ ] Assign only the approved retained and new access.
- [ ] Verify Engineering read-only access, Security monitoring access, and destination OU policies.
- [ ] Record sanitized evidence, expected results, actual results, and any differences; document rollback if needed.

## Leaver — John leaves NDIA

**Scenario:** John's employment ends after his transfer to Security Operations. His account must be disabled and his remaining Engineering and Security Operations resource access removed.

**Status:** Planned. Account disablement, access removal, and verification have not been executed in AD.

| Required field | Leaver control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner          | HR confirms the departure and effective date/time. An IT administrator disables the account, removes resource access, and verifies the result. The Technology Services and Security Operations resource owners confirm that John's access to their resources has been removed.                                                                                                                                                                                                                                                                                                                                                          |
| Trigger        | An authorized HR departure notification identifies `john.test` and the time access must end. An immediate termination request triggers immediate action.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Access change  | Record the current attributes, OU, resource-access memberships, and departure authorization. At the approved time, disable `john.test`, remove `Engineering_Project_Read`, `Security_Monitoring_Read`, and any other resource-access memberships or direct resource permissions assigned to John. Check for unexpected remaining Engineering write access and remove it if found. Close active sessions to the test file shares as applicable, then move the disabled account into the existing `DisabledUsers` OU. Retain the disabled account and change record for review; moving an account into this OU alone does not disable it. |
| Verification   | Confirm that the account is disabled and located in `DisabledUsers`. Check that the identified resource-access memberships and direct permissions have been removed. Confirm that a new domain-authenticated sign-in is denied and that John cannot access either test share, including through any previously active share session. Record expected and actual results; any remaining access is a failure requiring investigation.                                                                                                                                                                                                     |
| Rollback       | Do not automatically re-enable a departed employee's account after an error. If HR confirms that the departure was incorrect or cancelled, obtain authorized approval to restore access. An IT administrator restores the approved account attributes and OU placement, re-enables the account, and restores only the access justified by John's current role using the recorded state as a reference. Verify the restored access and record the reason and approvals. If departure remains valid, keep the account disabled while correcting incomplete access removal.                                                                |

### Planned execution checklist

- [ ] Confirm the authorized departure notification and effective date/time.
- [ ] Record the account's current state and identified resource access.
- [ ] Disable the account and remove resource-access memberships and direct permissions.
- [ ] Close applicable test-share sessions and move the disabled account to `DisabledUsers`.
- [ ] Verify that new sign-in and access to both test shares are denied.
- [ ] Record sanitized evidence, expected results, actual results, and any differences; record any approved restoration separately.
